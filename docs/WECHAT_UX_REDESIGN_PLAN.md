## 0. 直接回答两个问题

**Q2「加一个我的产物 tab 有必要没？」**
有必要，但**理由不是"怕东西丢"**，而且**现在直接加一定做错**。三条真实理由：

1. **产物现在没有身份。** `artifacts` 的版本号是按 `(conversation_id, type)` 递增的（`server/models.py:262` 的唯一约束）。同一个对话里写第二篇文章，会被记成 `article v2` —— 和"改了一版"无法区分。此时做产物列表，要么把两篇文章挤成一条版本历史，要么每版都列一条把用户淹掉。**必须先引入"作品（document）"这个一等公民，tab 才成立。**
2. **产物现在没有出口。** 「复制 HTML / 下载」有（`#copy-current-artifact`、`#download-current-artifact`），但「写入草稿箱」只绑在旧的 session 工作台上（`workbench.py:1708`），而新链路的 `.flow-actionbar` 被整块 `hidden`（`conversation-workbench.js:585`）。用户拿到 HTML 之后流程就断了。
3. **"不阻塞后续生成"不是 tab 能解决的。** 它靠的是**作品与流水线解耦**（作品入库即独立存在）+ **任务能在后台跑**。tab 只是这两件事的结果展示。

所以结论：**要加，但要按"作品中心"做，不能按"文件列表"做；顺序是先补数据模型与后台任务，再加 tab。**

**Q1「修复优化方案」** —— 一句话目标：**把"一个会聊天的表单"改成"一个有阶段的编辑器，配一个不会丢东西的作品库"。**

## 2. 目标：5 条体验原则

1. **说人话也能用。** 用户可以直接说"给我 10 个 AI 选题""第三段太长了""排版发我"，系统识别意图并**显式回显**"即将执行：选题"；识别不了才追问。
2. **任何一次点击都有回声。** 0.3 秒内出现状态（排队/进行中/第几步/预计耗时），失败必须出现在**对话流里**，带原因 + 重试。
3. **作品比对话长命。** 阶段一完成就入库；对话可以关，作品永远在；新文章永远不覆盖旧文章。
4. **不被绑定在同一条流水线上。** 可以同时有 2-3 个任务在跑，切 tab 不中断，回来能看到进度。
5. **每一步都是出口。** 选题、大纲、正文、HTML、图片，任意一步都能复制/下载/分享/基于它再开一篇。

### 用户真正要完成的三件事（JTBD）

- **J1 从 0 到一篇能发的稿子**：不想学流程，只想"给个方向→给我能发的"。
- **J2 改一处而不动全身**：已经写好了，只想动标题/第三段/开头。
- **J3 找回我用过的东西**：上周那篇 AI 文章，我要再发一次 / 基于它再写一篇。

> 现在的实现里，J1 勉强通、J2 完全不通、J3 不存在。改造优先级按 J1 → J3 → J2 排（J3 就是作品 tab，J2 是自由对话）。

## 3. 信息架构

```
顶栏：首页 · 公众号创作 · 作品 · 起号兽 · 小红书 · 贴图 · 爆文检测 · 早安祝福
                                   ↑ 新增（第 3 位），因为它是所有能力的出口
```

**「作品」放顶栏，不放头像菜单**：它是产出终点，不是设置。v1 只聚合公众号（`artifacts` 表已有的数据），但 schema 预留 `source`，二期把小红书/贴图/起号兽接进来 —— 那时它才真正值钱（现在这几个能力的产物互相看不见）。

### 公众号创作页的新布局

```
┌───────────────┬──────────────────────────────────────────┐
│ 对话 / 指令    │  阶段条：选题 → 大纲 → 正文 → 去AI → 配图 → 排版 │
│ （真·聊天）    │  ┌────────────────────────────────────┐  │
│               │  │  画布：当前阶段作品（可编辑/预览）    │  │
│ 消息流 +       │  └────────────────────────────────────┘  │
│ 阶段卡片       │  底部：本作品版本 / 导出 / 发布          │
├───────────────┴──────────────────────────────────────────┤
│ 全局任务 dock（右下角浮层）：其它会话正在跑的任务，可展开    │
└──────────────────────────────────────────────────────────┘
```

- 左边是**真聊天**（自由文本上下文化），右边是**结构化编辑**（阶段 + 画布）。
- 「我的作品」不再需要在这个页面里做入口 —— 顶栏有了；页面里只保留「本篇的版本」。

## 4. 数据模型：先让"作品"有身份（这是前置条件）

现状：`artifacts` = 每版一行，版本号按 `(conversation_id, type)` 递增，没有"这一篇"的概念。

### 4.1 方案（推荐 A）

**A. 加 `documents` 表 + `artifacts.document_id`（推荐）**

```
documents
  id            作品ID
  user_id
  conversation_id   创建它的会话（可为空，未来支持"从作品再创作"新建会话）
  title             作品标题（跟着最新 article 的标题走）
  kind              wechat_article / xhs_note / ...（预留多能力）
  status            draft / typed / published / archived
  cover_url         封面（有 image artifact 时冗余一份，列表页不用 join）
  created_at / updated_at / published_at
  metadata_json     预留
```

- `artifacts` 加 `document_id`（可空索引）。版本号改为 `max(version) where document_id = ? and type = ?`。
- **所有阶段产物都挂在同一 document 下**：选题 v1、大纲 v1、正文 v1/v2、报告、HTML、图片。列表只展示 `article/html`，其余折叠在详情里。
- 好处：一篇作品 = 一行；版本 = 该作品下同 type 的多个 artifact；跨会话聚合天然成立。

**B. 零迁移方案**：用 `artifacts.content_json.work_id` 塞。不推荐 —— 列表页要 `JSON ->>` 过滤，排序/分页无法走索引，且第二篇文章仍然分不出来。

### 4.2 历史数据回填（一次性脚本 `scripts/backfill_documents.py`）

- 对每个 `(conversation_id)`：按 `article` 的 `run_id` 分组 → 每个 run 一篇作品；`topic/outline/report/html` 按"最近的前一个 article run"归属；孤儿产物各成一篇 `kind=wechat_article, status=draft`。
- 旧数据里同一会话多篇文章本来就分不清，接受按 run 切分（比按 type 合并准确得多）。
- 回填幂等：`documents.metadata_json.backfill_key` 去重。

### 4.3 需要新增的接口（都只读 + 一个写）

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/documents?kind=&status=&q=&cursor=&limit=` | 作品列表（keyset 分页，按 `updated_at desc`） |
| GET | `/api/documents/{id}` | 作品详情：当前稿 + 阶段产物 + 版本列表 + 可执行动作 |
| GET | `/api/documents/{id}/versions?type=article` | 版本时间线 |
| POST | `/api/documents/{id}/publish` | 写入公众号草稿箱（复用 `scripts/workbench-skill-publish.py`） |
| PATCH | `/api/documents/{id}` | 改标题 / 归档（软删） |
| POST | `/api/documents/{id}/derive` | 基于此作品新建会话（引用原稿，不复制内容） |

`artifacts.user_id` / `conversation_id` 已有索引，`documents(user_id, updated_at desc)` 加一个复合索引即可，列表页不会成为慢查询。

## 5. 主流程（改造后）

### 5.1 一次正常创作

```
输入"我想写 AI 相关的" 
  → 意图识别：选题（回显"即将执行：生成 10 个方向"）
  → 后台 Run：选题 → 入作品库（作品A，status=draft）
  → 结果以"选题卡片"回到对话流（10 个方向，可点选/可"再换一批"）
用户点第 3 个方向
  → 大纲 → 入作品库 → 卡片：大纲（可编辑，保存即新版本）
  → 一键"继续写正文"（不需要回画布点按钮）
正文完成 → 卡片：正文（含"改第三段"输入框，直接走 revise）
  → 去 AI → 卡片：修订稿 + 复核摘要（默认折叠）
  → 配图（可选）→ 卡片：图片网格
  → 排版 → 卡片：HTML 预览 + 三个出口（复制/下载/发草稿）
```

**关键差异**：每一步是**对话流里的一张卡**，不是"切到右边另一个视图找按钮"。画布只做"深度编辑"，不承担流程。

### 5.2 失败与恢复

```
run.failed
  → 对话流插入红色卡片：
     「选题这一步没跑完」+ 原因（人话）+ 折叠的技术信息（error_code）
     + [重试这一步] [换个方向] [查看详情]
  → 重试复用同一 stage + 同一 document，不新建作品
  → 上游已完成的阶段保留，"重试"只重跑失败节点
```

### 5.3 离开 / 并行（"不阻塞"的真正实现）

```
用户点「新写作」→ 新建会话（旧会话的 run 继续在后台执行）
  → 右下角全局 dock 显示：「文章A · 正在排版 60%」「文章B · 排队中」
  → 切到「作品」tab，能看到 A 的状态实时变化（生成中/已完成/失败）
  → 任何页面刷新，dock 从 /api/runs?status=active 重建
```

后端天然支持：`runs` 本来就独立于页面、有 `celery_task_id` / `heartbeat_at`（`models.py:195`）。缺的是**一个"我的进行中任务"查询**和**前端不再在切会话时 `closeEvents()` 把任务状态丢掉**（`conversation-workbench.js:340`）。

### 5.4 找回与再创作（J3）

```
作品 tab → 搜索"AI" → 卡片「AI 到底会不会取代我（3 版 · 已排版）」
  → 点开：正文/HTML/图片三个分段 + 版本时间线
  → 操作：继续编辑（回到原会话）｜复制 HTML｜下载｜发草稿｜基于此再写一篇
「基于此再写一篇」= POST /api/documents/{id}/derive → 新会话，把原作作为参考上下文
```

## 6. 「作品」tab 规格

### 6.1 列表

- 一行 = 一篇作品（不是一版）。默认按 `updated_at desc`，keyset 分页（游标 = updated_at + id），一次 20 条。
- 卡片字段：**标题**（无标题用"未命名 · 10-22"）、状态徽标（草稿/已排版/已发布）、`3 版`、更新时间（今天 14:20 / 昨天 / 10-18）、**阶段进度条**（选题✓大纲✓正文✓去AI·配图·排版 6 格）、缩略（有封面用封面，没有用首段文字排版稿）。
- 顶部：搜索（标题 + 正文全文，`ILIKE`，P2 再上 pg_trgm）、状态筛选、时间筛选、能力筛选（v1 只有公众号）。
- 空状态：一句话 + 「开始写第一篇」。
- 列表项右侧 hover 操作：继续编辑 / 复制 HTML / 更多（下载、发布、归档）。

### 6.2 详情（右侧抽屉或独立页，二选一，推荐独立页可深链 `/works/{id}`）

- 头部：标题（可改）、状态、时间、操作条（继续编辑 / 复制 / 下载 / 发草稿 / 再写一篇）。
- 主体三个 tab：**正文**（可编辑，保存即新版本）/ **排版 HTML**（iframe 预览，与公众号一致）/ **图片**。
- 版本时间线：按 type 分组，点任一版可"恢复此版本"（复用 `create_artifact_version`）。
- 折叠区：选题、大纲、复核报告（这些是过程材料，不占列表）。

### 6.3 明确不做（v1）

- ❌ 文件夹/多级分类/标签树 —— 搜索 + 时间足够，做树只会增加维护负担。
- ❌ 把选题、大纲、报告当成"作品"列出来 —— 它们是阶段产物，只在详情里出现。
- ❌ "导出全部"、协作/分享链接 —— 等有人开口要再做。
- ❌ 回收站 —— 先做 `archived` 状态 + 确认弹窗，够用。

## 8. 验收标准（先写测试再改）

1. 失败路径：`orchestrator` 工具抛错 → 存在 assistant 消息 + `run.error_code` 在事件里；浏览器测试断言错误卡片出现（现在 `test_workbench_stages_browser.py` 只 mock `run.completed`，失败零覆盖）。
2. 选题：热点脚本抛异常 → run 仍 `completed`，artifact 标注 `search_status=unavailable`；7 条也通过。
3. 作品：同一会话连写两篇 → `documents` 两行，各自版本从 1 开始（**这是当前模型做不到的核心回归**）。
4. 不阻塞：会话 A 的 run 进行中 → 新建会话 B 提交 → A 仍完成，dock 两行状态正确。
5. 出口：排版 → 复制/下载/发草稿三件事都可用，发草稿成功后作品 `status=published`。

## 9. 风险

- **回填质量**：旧数据同一会话多篇文章无法还原，按 `run_id` 切分是近似。建议回填后跑一遍"作品数 vs 会话数"的抽查，异常会话人工标记。
- **两套引擎并存**：P0 阶段先不动 `/api/workflows`，但 P2 必须删，否则新加的作品入口会再次出现"同一个按钮两套 handler"（现在 `app.js:983` 就在抢 `#start-workbench`）。
- **发布是外部副作用**：`publish` 必须幂等（现 `workbench.publish` 用 `media_id` 去重，抽出来时保留），且永远只写草稿、不群发。
- **不要一次上自由对话**：模型自主选工具会把"每阶段必调一次工具"的确定性打掉，先做意图路由（确定性），再放开（概率性）。
